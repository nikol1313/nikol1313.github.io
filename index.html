iPhone Tracker.ge
Read more Show less
The problem

When buying an iPhone, the same model costs different amounts at different stores, and prices change often. Checking every site by hand took a lot of time, and I still didn’t know whether it was a good moment to buy. So I built an app that collects prices automatically, keeps their history, and notifies me when a price drops to my target.

What I built
  • Retailer-specific scrapers refresh the catalogs of 8 stores (Zoommer, Alta, iSpace, Elit Electronics, Megatechnica, Extra.ge, PCShop, Metromart) every 12 hours, and a parser recognizes differently worded titles, such as “Apple iPhone 17 (8GB/256GB) - Sage” and “iPhone 17, 256 GB, Sage”, as the same model, storage, and color.
  • A Python, FastAPI, and async SQLAlchemy backend stores every price change in PostgreSQL and, based on 90 days of history, decides: “Buy now or wait?”
  • Registered users can track phones and set a target-price or back-in-stock alert, delivered to their verified email.
  • Authentication is protected by per-IP rate limiting. After 5 wrong passwords the account is locked for 15 minutes, and password reset links are single-use and expire in one hour.
  • A responsive vanilla JavaScript interface offers filters, a side-by-side comparison of two phones, and recommendations based on intended use. Docker Compose and Nginx run the whole system, and pytest and HTTPX test the API.

Video Downloader
Read more Show less
The problem

Growing up, I downloaded songs to my device from the “YouTube to MP3” sites that come up on Google, but they were full of ads and sometimes viruses. So I built my own clean downloader that fits my preferences and runs long downloads in the background.

What I built
  • yt-dlp downloads videos from YouTube and other supported sites in 360p, 720p, or 1080p, or as audio-only MP3, and FFmpeg merges video and audio.
  • A Node.js, Express, and TypeScript backend runs yt-dlp as background processes, two at a time, while PostgreSQL stores every download job.
  • A one-page React and TypeScript interface starts downloads, shows live progress, and saves finished files.
  • Prometheus collects app metrics at /metrics, and Docker Compose runs the whole stack.
  • GitHub Actions CI builds the app and runs integration tests against PostgreSQL on every push, including checks that invalid input is rejected.

AlteX
Read more Show less
The problem

The Alte University student portal works, but it is hard to use: a dated design, cluttered pages, confusing navigation, and a timetable that is difficult to read. I open it every day, so I redesigned it.

What I built
  • Before each release I went through the portal’s pages by hand on desktop Chrome and on Android phones. One QA pass alone found search placeholders that were invisible on the dark theme, tables cut off on narrow screens, links smaller than a 44px touch target, low-contrast captions, and an Android back button that stopped working after the app was sent to the background.
  • I measured a freeze on the programme page and cut it from 2.5 s to 1.5 s by skipping layout for off-screen modules, and added an offline screen and a notice for outdated WebViews.
  • A Manifest V3 extension injects CSS and content scripts that restyle the dashboard, timetable, grades, finances, registration and login pages. It only reads what the portal already shows and sends nothing anywhere else.
  • The Android app loads the portal in a WebView and injects the same extension code, built straight from manifest.json, so there is one codebase to test. GitHub Actions builds an APK on every push and publishes a signed one to GitHub Releases on a version tag.
  • Playwright tests inject the extension into fake portal pages, so no real student account is needed. They check the login page, grade and counter tagging, labels for icon-only buttons, the exam countdown with a frozen clock (before, during and after an exam period), and that no request leaves the portal’s host.
